# Divergences found in ticket 08

A line number in `src/` refers to the code at commit `fb437d0d`, the commit before this ticket.

## D08-1 — A JSON call to a model that cannot give JSON fails, and does not succeed with prose

- **Where:** `src/pipeline/stages/model-stage.ts:105` (`tryJsonReply`), found in ticket 08.
- **The code does:** a `"json"` call sends `provider: { require_parameters: true }` beside `response_format` (`src/pipeline/openrouter.ts:110–118`, `responseFormatFields`). OpenRouter then sends the call only to an endpoint that supports every parameter. A model with no such endpoint fails the call.
- **The intent says:** the old comment, quoted here:

  ```text
  JSON mode is a routing preference rather than a guarantee, so a model whose providers cannot honour it answers in prose and the request still succeeds — the stage would then be reading fields off a sentence (technical-design.md §6).
  ```

- **Other sources:** technical-design.md §6, "JSON mode is routed for as well as asked for", agrees with the code. It says: "A model that cannot do JSON then fails the call". The same section says that a reply that will not parse is a stage failure. So the check in `tryJsonReply` stays useful.
- **Status:** open

## D08-2 — A cut can move back onto the previous cut

- **Where:** `src/pipeline/stages/division.ts:220` (`overLeadingConnectives`, parameter `notBefore`), found in ticket 08.
- **The code does:** the word loops stop at `begin > notBefore`, so `begin` can equal `notBefore` (`division.ts:236–238`). When that word is a connective, `before` is `""` and the function returns `begin`, which is the previous cut (`division.ts:246–249`). The next subtopic then has no text. `assertLossless` accepts a subtopic with `end === start` (`division.ts:335`).
- **The intent says:** the old comment on `notBefore`: "The previous cut, which this one may never reach."
- **Other sources:** technical-design.md §5, "Finding the start words", says nothing about the previous cut. CONTEXT.md, Subtopic, says a subtopic is "one continuous stretch of transcript on a single point", which an empty subtopic is not.
- **Status:** open

## D08-3 — A failed run does not lose the runs in flight

- **Where:** `src/pipeline/stages/panel-runs.ts:191` (`runPanel`), found in ticket 08.
- **The code does:** `runPanel` makes its runs through `mapWithConcurrency` (`src/utils/concurrency.ts`). When a run fails, no further run starts, but the runs in flight finish. Each one is saved inside `work` (`panel-runs.ts:216–217`) before the failure is thrown. Only a crash loses the runs in flight.
- **The intent says:** the old comment: "a crash or a failed run loses only the runs in flight".
- **Other sources:** technical-design.md §5, "Dividing the transcript", Panel runs, agrees with the code. It says:

  ```text
  Runs already in flight are let finish, and are saved, before the stage fails
  ```

  The comment on `mapWithConcurrency` agrees with the code.
- **Status:** open

## D08-4 — `readPanel` reads only splitting panels

- **Where:** `src/pipeline/stages/panel-runs.ts:244` (`readPanel`), found in ticket 08.
- **The code does:** the only production caller of `readPanel` is `readTranscriptAndRuns` (`src/pipeline/stages/stage-input.ts:158`), which reads a splitting panel. `group-into-topics` chooses its grouping from the runs that `runOneCallPanel` gives back, and never reads a grouping panel through `readPanel`.
- **The intent says:** the old comment, quoted here:

  ```text
  A stage that goes on from a panel needs all of it, because a missing run changes what the vote or the modal grouping means
  ```

- **Other sources:** technical-design.md §5, Panel runs, says "a missing run changes what the vote means", with no word about the grouping. CONTEXT.md lists "modal grouping" as a word to avoid.
- **Status:** open
