## D10-1 — `source-normalisation` logs the numbering and the matches at `debug`, not at `info`

- **Where:** `src/pipeline/stages/source-normalisation/source-normalisation.ts:298` (the "Resolved lecture" log in `normaliseModule`), found in ticket 10.
- **The code does:** each lecture's number, date, source pair and provisional title go to `logger.debug` (`source-normalisation.ts:298–309`). At `info`, the stage logs these:
  - the counts of source files (`:248–251`)
  - each rename (`:321–323`)
  - each manifest write (`:331–336`)
  - each deletion (`orphaned-workspaces.ts:160–168`).

  The integration test "should record each lecture's date, number and matched sources when normalisation succeeds" reads these lines at `debug`.
- **The intent says:** technical-design.md §5, `source-normalisation`, Logging (line 1024). It says: "Every action — files discovered, dates extracted, numbers assigned, matches, … — is recorded at `info`".
- **Other sources:** the old comment at `source-normalisation.ts:293–297` cites technical-design.md §10 for these lines. §10, Debug Log File, does not list them.
- **Status:** open

## D10-2 — `source-normalisation` can throw after it has changed files

- **Where:** `src/pipeline/stages/source-normalisation/source-normalisation.ts:47` (`SourceNormalisationError`) and `:234` (`normaliseModule`), found in ticket 10.
- **The code does:** `normaliseModule` first calls `completeInterruptedRenames` (`:236`). That function renames each temporary entry to its target when no target is taken (`source-renames.ts:109–115`). After that, the stage checks the source rules (`:253–261`) and asks about orphaned workspaces (`:272–283`). So a broken source rule or a declined deletion can throw after a file was renamed.
- **The intent says:**
  - the old comment on `SourceNormalisationError` (`:44–45`): "the stage makes no filesystem changes when it throws".
  - the old TSDoc of `createSourceNormalisationStage` (`:215–216`): "when invalid it logs every problem and throws without touching the filesystem".
  - technical-design.md §5, `source-normalisation`, line 999: "If any check fails it logs every problem found … and throws, making **no filesystem changes**".
  - technical-design.md §5, the code block, line 1036: "Throws SourceNormalisationError on any … declined confirmation, having made no filesystem changes."
- **Other sources:** technical-design.md §5, "Collision-safe renaming" (line 1020), agrees with the code. It says: "A run therefore begins by finishing any rename its predecessor was interrupted partway through".
- **Status:** open

## D10-3 — A new lecture's manifest has no cost

- **Where:** `src/pipeline/stages/source-normalisation/source-normalisation.ts:155` (`initialManifest`), found in ticket 10.
- **The code does:** `initialManifest` writes the identity fields, the three titles, `createdAt`, `updatedAt` and `stages` (`:155–171`). `pendingStages` gives each stage `{ status: "pending" }` (`src/pipeline/manifest.ts:76–78`). The `Manifest` type has no cost field outside the stage entries.
- **The intent says:** the old comment (`:147–150`): "every stage pending, and zeroed cost".
- **Other sources:** technical-design.md §5, `source-normalisation`, step 6, agrees with the code. It lists the fields of the initial manifest and names no cost. `Manifest.stages` in `src/types/pipeline.ts` says: "Nothing adds the stage costs together (NFR-2.2)."
- **Status:** open

## D10-4 — The numbering is in `lecture-resolution.ts`, not in the stage

- **The code does:** `orderLectures` in `lecture-resolution.ts` sorts the source pairs by date. It gives each lecture its number (`:228–251`). `source-normalisation.ts` calls it (`:285–292`). Manifest seeding (`initialManifest`, `reconcileManifest`) is in `source-normalisation.ts`.

  - the old header of `source-normalisation.ts` (`:10–11`) agrees with the code: "which lecture is Lecture 1 in `lecture-resolution.ts`".
