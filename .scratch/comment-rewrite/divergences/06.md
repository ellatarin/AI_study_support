# Divergences found in ticket 06

A line number in `src/` refers to the code at commit `fb437d0d`, the commit before this ticket.

## D06-1 — Nothing branches on `ContextLengthError`, and its own message gives the advice

- **Where:** `src/pipeline/openrouter.ts:51` (`ContextLengthError`), found in ticket 06.
- **The code does:** the error's message gives the advice (`toProviderError`, `openrouter.ts:261–264`). The message ends: "Configure a larger-context model for this stage in pipeline-config.json". Only `openrouter.ts` and its test name `ContextLengthError`. The runner records it as it records any stage failure.
- **The intent says:** the old comment: "Surfaced as a distinct type so the runner can advise switching to a larger-context model". It goes on: "rather than treating it as a generic failure (technical-design.md §8)".
- **Other sources:** technical-design.md §8, API Error Handling, agrees with the code. It says: "Stage fails with a message advising the user to switch to a larger-context model in config". The §6 client surface says only that context length "has a remedy of its own".
- **Status:** open

## D06-2 — Not every error of `callModel` names both the model and the stage

- **Where:** `src/pipeline/openrouter.ts:474` (`callModel`, the last `@throws` line), found in ticket 06.
- **The code does:** the `ContextLengthError` message names the model and not the stage (`openrouter.ts:262–264`). The `UnconfiguredStageError` message names the stage and not a model (`unconfiguredStageMessage`, `src/utils/stage-config.ts`). `ProviderError` and `NoReplyChoicesError` name both.
- **The intent says:** the old comment: "Every one of these names the model and the stage in its message (§8)."
- **Other sources:** technical-design.md §8, API Error Handling, says only that for an unavailable model the "model ID [is] included in error message". It makes no statement about every error.
- **Status:** open

- **Status:** open

## D06-6 — A failed send whose reply has no numeric cost is recorded as costing nothing

- **Where:** `src/pipeline/openrouter.ts:347` (`replyCost`), found in ticket 06.
- **The code does:** `replyCost` returns `{ costUsd: 0 }` when `hasProviderError` is true and `usage.cost` is not a number (`openrouter.ts:354–359`). So a failed send with no reported cost is recorded at zero.
- **The intent says:** `CONTEXT.md`, entry Send (line 181): "Every send is billed."
- **Other sources:** technical-design.md §6, "A rejection can arrive inside an accepted reply", agrees with the code: "when it reports none it is counted as costing nothing, because OpenRouter does not bill a request that produced no output".
- **Status:** open
