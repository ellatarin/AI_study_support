# Divergences found in ticket 04

Line numbers in `src/` refer to the code at HEAD (`fb437d0d`), the commit before ticket 04.

## D04-1 — The manifest header says the manifest holds "accumulated cost"

- **Where:** `src/pipeline/manifest.ts:4` (file header), found in ticket 04.
- **The code does:** each stage entry holds the cost of one completion only. `complete` writes `cost: result.cost` (`createStageStatusWriter`, `src/pipeline/runner.ts:437–441`). `skipped` copies the cost of the earlier completion (`skippedEntry`, `runner.ts:318–336`). A `--from-stage` reset sets the entry to `pending`, which has no cost (`resetFromStage`, `runner.ts:546–565`). No code adds costs together.
- **The intent says:** the old comment: "The manifest is the pipeline's single record of a lecture's identity, stage states, and accumulated cost".
- **Other sources:** technical-design.md §4.5 agrees with the code. It says that the manifest tracks "the cost of the most recent successful execution of each stage". It also says that "the manifest holds no roll-up of them".
- **Status:** open

## D04-2 — `workspacePath` has no caller outside its own test

- **Where:** `src/pipeline/workspace-paths.ts:49` (`workspacePath`), found in ticket 04.
- **The code does:** `vera references workspacePath` and `vera grep "workspacePath\b" --path "src/**"` find only `src/pipeline/workspace-paths.integration.test.ts`. No production code calls it. Stage output paths come from `src/pipeline/layout.ts`.
- **The intent says:** the old comment: "The trusted door. Used for internal, code-supplied paths — a stage's own output directories, say". technical-design.md §4.4 calls the module "the two path resolvers, one per kind of input". It also says: "Keeping the trusted resolver beside the untrusted one is deliberate".
- **Other sources:** implementation-plan.md lists `workspacePath` with `resolveManifestPath` (TD §4.4). No source says that nothing calls it.
- **Status:** open

## D04-3 — `assembleContext` says one context is shared by every stage of a pipeline run

- **Where:** `src/pipeline/stage-context.ts:23` (`@returns` of `assembleContext`), found in ticket 04.
- **The code does:** the runner builds a new context after each write to the manifest (`createStageStatusWriter`, `src/pipeline/runner.ts:427`). `#runStages` gives each stage the context that the stage before it left (`runner.ts:795–810`).
- **The intent says:** the old comment: "The frozen stage context shared by every stage in the run."
- **Other sources:** technical-design.md §4.7 agrees with the code: "The context is **rebuilt between stages** rather than assembled once for the run". The old header of `stage-context.ts` agrees with the code: "The runner assembles a fresh context at every stage transition".
- **Status:** open

## D04-4 — The runner runs the lecture stages in the order of `lectureStages`, not `STAGE_IDS`

- **Where:** `src/pipeline/runner.ts:88–91` (the line comment before `deriveTimestampId`) and `runner.ts:796` (`#runStages`), found in ticket 04.
- **The code does:** `#runStages` walks `this.#lectureStages`, the array that the caller injects. Nothing checks that its order is the order of `STAGE_IDS`. Only the `--from-stage` reset (`runner.ts:558`) and the `--to-stage` bound (`isStageAfter`) use `STAGE_IDS`.
- **The intent says:** the old comment: "Pipeline order comes from STAGE_IDS, the declared source of truth". technical-design.md §4.7, "Pipeline order comes from `STAGE_IDS`", says that everything that walks the stages in order "iterates that array". It also says: "the pipeline's order has one statement".
- **Other sources:** technical-design.md §4.7 shows `lectureStages` as an injected constructor argument. The `deps.lectureStages` TSDoc says "in execution order". The user's build notes say that `lectureStages` is pipeline order.
- **Status:** open
